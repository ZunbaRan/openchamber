# Interactive UI server runtime

This module owns Local and Hosted OCIX discovery, Interactive UI/HTML Artifact assets, Agent Runtime ownership, and the Business Gateway. Standard MCP Apps are handled by the OpenCode fork and the UI MCP App host; they do not enter this OCIX runtime.

## Style v2 (2026-08-06)

The built-in Agent Tools and Skill follow the frozen visual contract in `docs/OCIX_STYLE_CONTRACT.md`:

- `builtin/agent-runtime/tools/interactive_ui.ts` accepts optional `layoutMode` (`dashboard-hero` / `master-detail` / `report`) with fail-closed slot validation (unknown mode/id, missing required slot, duplicate ids, KPI count > 4 all reject), plus `emphasis`/whitelisted `icon` on metrics, `density`/`toneColumn` on tables, and `referenceValue`/`referenceLabel` on charts. Local-interactivity fields are presentation-only and never reach the Gateway: `searchable`/`sortable`/`pageSize` (table), `filterable` (list), `orientation=vertical` (flow), `stacked` (bar chart).
- `builtin/agent-runtime/tools/interactive_ui_gallery.ts` takes an optional `mode` arg (`components` default, or one of the three layout-mode demos).
- `builtin/agent-runtime/skills/interactive-ui-visualization/SKILL.md` carries the composition guidance (one focal point, KPI ≤ 4, slot table, mode selection).
- `builtin/agent-runtime/skills/html-artifact-design/SKILL.md` (built-in v1.3.0) is the HTML Artifact design guide for first- and third-party authors: full token-slot consumption, typography, composition discipline, chart color order, sandbox-safe motion. Third-party authors get the same rules via the developer guide §5.8 and the updated artifact template.

## Extension roots

The runtime discovers extensions from:

1. `<OPENCHAMBER_DATA_DIR>/extensions`
2. each path in `OPENCHAMBER_INTERACTIVE_UI_EXTENSIONS_DIR`, separated by the platform path delimiter

Each root may be one extension directory or a directory containing extension directories. Discovery is read on demand in v1 so development manifest/view changes are visible without a server restart.

Managed packages have three delivery modes:

- `local`: the signed `.ocix` contains all reviewed runtime assets, Tools, Skills, and descriptors.
- `hosted`: the signed thin `.ocix` contains publisher/app identity, manifest URL, initial permission summary, update policy, and minimum runtime version. The remote signed `HostedOcixManifestV1` supplies versioned surfaces/actions/resources; only bounded last-good resources are cached locally.
- `remote` (Phase R1): the appEntryUrl is a direct signed Hosted OCIX Manifest URL — no thin package and no handshake indirection. The signed payload carries the publisher envelope (`publisher: { id, name, keyId, publicKey }`). The manifest signature is verified with that embedded Ed25519 key, the key is normalized with the package-format helpers, and the fingerprint is derived locally (a fingerprint string from the server is never trusted). The signature `keyId` must equal `publisher.keyId`.

Remote connect persists only a small host-managed discovery shell — the signed Manifest, `openchamber.extension.json`, and host-generated Agent Runtime shims — plus trust, approved/granted permissions, accepted Manifest metadata (including the connect `installationId`), appEntryUrl, connector refs, and timestamps. Connect, inspect, and list stay metadata-only: they never fetch or persist `resources[]`, and there is no installed resource tree in the shell. The declared signed resources stay lazy (Phase R2): on the FIRST actual load of a runtime entry (declarative JSON, Native ESM, installed HTML Artifact, or icon), exactly one requested signed resource is fetched, verified, and cached — see "Remote lazy signed resource loading" below. Phase R1 supports exactly one connector with `auth.type === "api-key"`; zero or multiple eligible connectors are rejected with stable error codes. A publisher is reported as trusted only when the stored trust record carries exactly the candidate key (the stored public key is re-normalized and re-fingerprinted locally); a same publisher/keyId slot occupied by a different key inspects as untrusted and connect rejects it with `publisher_key_conflict` before any write.

Remote health and signed-manifest updates (Phase R3): the signed manifest kernel may carry optional `update: { required?, changeSummary? }` metadata (covered by the signature; normalized to safe `required`/`changeSummary` defaults, and invalid values reject with `invalid_hosted_manifest`). The manager exposes `checkRemoteUpdate`, `applyRemoteUpdate`, `prepareRemoteUse`, and `getRemoteLifecycle` — see "Remote lifecycle probes and updates (Phase R3)" below. Health/update probes are bounded (45s TTL, coalesced, never holding the mutation queue during network I/O); automatic metadata-only apply happens only for same-key none/reduced candidates; permission expansion, nativeCode 0→1, and key rotation require re-consent; required updates block use until a valid confirmed update applies; unreachable entry health keeps the old signed contract usable.

## Remote lifecycle probes and updates (Phase R3)

Health/update automation is manager-owned and bounded. A Remote lifecycle probe captures the current authority/trust state under a SHORT mutation-queue phase, performs ALL network verification (manifest fetch + full signed verification + write-free preflight + exact-one-api-key connector selection) OUTSIDE the global mutation queue, and revalidates the current generation/accepted manifest hash before any store/apply — AFTER EVERY network attempt a short mutate/capture phase compares the current generation + accepted manifest hash + appEntryUrl with the probed snapshot and discards/re-probes the stale classification before storing or returning it — the bounded loop allows at most TWO network attempts: after attempt 2 a further contract change caches NOTHING and fails closed with the stable controlled `remote_update_generation_changed` error; only a probe whose snapshot passed the immediate post-network comparison is stored/returned, with the FULL subject (generation + acceptedManifestHash + appEntryUrl) propagated everywhere (cache entries, joined comparisons, re-probes); the RETURNED snapshot is the freshly captured post-network `current` (the probe is valid for the same immutable contract, but `current` carries the latest same-contract persistedBlockedUpdate and other safe state, so callers never act on a stale pre-network block snapshot) — one slow or broken Remote never blocks unrelated manager operations. Probe results (safe success AND safe failure status) live in a process-lifetime 45-second TTL cache with a fixed cap and deterministic oldest-first eviction; same-extension in-flight probes coalesce (the slot is reserved synchronously before any await; ONLY genuine network probes occupy the in-flight slot, so a force:true call always bypasses a settled TTL entry and can never join a mere cache-resolution), and manual `force` bypasses a settled TTL entry while still joining a genuine current network probe. All cache time boundaries are INCLUSIVE and the clock is validated/injected in tests: timestamps must be non-negative safe integers within ECMAScript Date's representable range with TTL-safe arithmetic (NaN/Infinity/fractional/negative/out-of-Date-range/overflow values yield checkedAt null, skip caching, and never throw); a backward clock regression (now < cachedAt) is a cache MISS, never a hit.

- `checkRemoteUpdate(extensionId, { force })` verifies/classifies only with respect to applying contracts/resources (nothing is ever applied and no resource bytes are fetched), but EVERY freshly verified, reachable, structurally valid signed candidate whose RAW probe status is `required` ATOMICALLY persists safe `blockedUpdate` metadata BEFORE the API reports success (reason `confirmation-required` when consent is needed, `required-observed` otherwise), and the returned lifecycle is consistent with the durable state (`status: 'required'` plus `blocked.code: 'remote_update_required_blocked'`); persistence is subject-safe (generation + acceptedManifestHash + appEntryUrl revalidated inside the mutation queue) and a contract change during persistence discards the stale observation and re-resolves boundedly, failing closed with `remote_update_generation_changed` if stabilization is exhausted. A fresh verified REACHABLE non-required candidate SUPERSEDES and clears an obsolete persisted required block (classification only), so the dynamic root can return and the next surface trigger can auto-apply; an unreachable probe or candidate failure keeps the block fail-closed; clearing is EXACT-MATCH (the current persisted block is compared field-for-field — version/hash/reason/observedAt — against the block captured in the probe snapshot inside the same mutation-queue slot) and returns a result, so a lost stale-clear race (a newer required block persisted under the same installed generation/hash) makes the check RE-RESOLVE and never report unblocked while a newer block remains. Result fields: `status: 'none' | 'available' | 'required'`, current/remote version+manifest hash, `changeSummary`, `permissionDelta: 'none' | 'expanded' | 'reduced'`, safe `addedPermissions` diff, `keyChanged`, `requiresUserConfirmation`, candidate `publisherFingerprint` (needed for exact confirmation), and `health: { status: 'unknown' | 'reachable' | 'unreachable' | 'trust_invalid', checkedAt, code? }`. Deterministic candidate failures (version reuse, unauthorized downgrade, publisher identity change, same-keyId trust conflict, connector identity change) throw stable actionable errors; trust/network conditions are classified into health. No public key, signed document, internal path, installationId/generationId, credential, raw upstream body, or unsanitized error text is ever exposed.
- `prepareRemoteUse(extensionId, { trigger, force })` (runtime trigger matrix: startup/surface/Workbench/manual) runs the check and AUTOMATICALLY applies only same-key none/reduced candidates (metadata-only). An ordinary available update awaiting consent keeps the old contract usable. A required update that cannot apply — or required+expansion awaiting consent — is BLOCKED with an actionable stable error (`remote_update_required_blocked`) and the safe pending/blocked metadata needed to prevent bypass is PERSISTED. A persisted required block does NOT deadlock the automatic apply when the CURRENT RAW probe is reachable, valid, status=required, and requiresUserConfirmation=false: prepareRemoteUse proceeds through the existing metadata-only automatic apply (covering a manual check observation or an earlier apply-failed block), switching exactly once and clearing the obsolete block with the new version record; the block is NOT bypassed for unreachable/trust-invalid/candidate-failure/RAW non-required probes, and required+confirmation stays blocked until an explicit apply. After a successful apply/generation switch the obsolete block never governs the new active contract and roots/runtime use recover. Failed auto-applies are TOCTOU-RECLASSIFIED FORCED (bypassing the stale 45s entry) against the CURRENT signed candidate: an OPTIONAL update whose apply refetch becomes expansion/key-rotation returns as ordinary pending-consent (old contract usable), becomes unreachable stays old-contract-usable, or fails atomic staging/commit returns as NOT applied without a tight retry loop (a later trigger may retry); only a FRESH required candidate persists/blocks, and deterministic invalid/trust candidates fail closed. An INITIALLY REQUIRED candidate whose apply refetch changes to confirmation-required is also reclassified forced: a reachable valid non-required candidate supersedes it (old contract usable pending consent, no stale block persisted), a fresh required candidate persists/blocks, and unreachable or invalid cannot bypass the previously observed required update (persist/block with the safe verified metadata). `remote_update_none` from a concurrent apply remains a safe no-op (never a stale-snapshot block); `remote_update_generation_changed` (the active contract changed while this prepare was in flight) returns applied:true/contractChanged so every runtime trigger re-runs discovery — the caller did not perform the write, but it never continues with the stale pre-prepare descriptor/authority. The optional failed-apply reclassification also FAILS CLOSED on fresh trust_invalid (e.g. publisher_untrusted with no update.failure) exactly like the top-level path. The exact previous active version, accepted manifest, approved permissions, trust, and shell are preserved by every failed apply. `trust_invalid` and deterministic candidate failures fail closed; unreachable entry health still allows the old signed contract to render UNLESS a previously observed required update is persisted (the network cannot be used to bypass it). Rejection/dismissal performs no apply: `acceptedManifest` and `approvedPermissions` stay exactly old.
- `applyRemoteUpdate(extensionId, { confirmedManifestHash, confirmedPublisherFingerprint })` refetches and reverifies (TOCTOU-safe), requires the EXACT candidate manifest hash and publisher fingerprint whenever confirmation is needed (permission expansion, nativeCode 0→1, key rotation), and atomically installs a new metadata-only Remote shell (signed manifest + `openchamber.extension.json` + host-generated Agent Runtime shims ONLY; ZERO declared UI/artifact/resource bytes). Connector id and api-key auth type must stay stable (no silent credential rebinding); a changed manifest must use a different semver; a lower semver is allowed only for signed `update.required` (security rollback). The installation-bound credential identity is reused verbatim, a NEW private lifecycle generation is created, the previous version stays installed for rollback, and on ANY failure the exact previous active version, acceptedManifest, approvedPermissions, trust, Agent Runtime state, and usable shell are preserved. A new keyId is trusted only after exact fingerprint+manifest confirmation; the OLD key is kept so rollback remains verifiable; same keyId with a different fingerprint is `remote_trust_conflict` (a trusted key is never silently replaced), and a DIFFERENT current keyId whose trust-store slot is already occupied by a different fingerprint/public key is ALSO classified `remote_trust_conflict`/trust_invalid during check and apply (re-consent would be impossible — the slot can never be overwritten). Successful apply naturally misses old resource cache entries (keys include the new manifest hash) with no eager download or compatibility fallback.
- `getRemoteLifecycle(extensionId)` returns the same safe summary for reads; `getEnabledExtensionRoots` never issues a Remote root while its persisted status is blocked by a required update, and enabling fails closed too. The manager `list()` merges the SAFE cached lifecycle summary and persisted block into the sanitized Remote metadata (never triggering network work in a read-only list).
- The runtime receives `prepareExtensionUse`/`getExtensionLifecycle` callbacks: surface/artifact descriptor/document/icon loads, third-party Workbench prepare/migrate/catalog paths, and `invokeAction` call the prepare BEFORE serving/acting and RELOAD discovery when an automatic update switched the active manifest. Before the real business request, `invokeAction` requires a cached/coalesced connector test when the connector declares one (any health failure returns an actionable stable error and sends ZERO business action request). Connector tests are cached/coalesced for 45 seconds with bounded storage; manual tests force fresh probes. Non-2xx connector-test and action responses are classified IMMEDIATELY after the fetch, BEFORE reading/retaining the body (a hostile or throwing 401/403 body still maps unauthorized/forbidden and is never consumed); 2xx body-read failures are wrapped as stable actionable unreachable upstream failures (cached for connector tests with the true checkedAt; for actions, prior preflight evidence is detached before recording the failure so stale completion cannot overwrite it). Test evidence is AUTHORITY-SAFE: the current connector and effective endpoint are resolved BEFORE any settled or in-flight entry is accepted, and every cached/in-flight entry is bound to a deterministic SAFE subject (effective origin/base URL, test method/path, auth type, declared auth placement/config contract — never accessKey, environment token values, custom header values, or other credentials), so a Remote manifest update that keeps the connector id/auth type can never reuse old evidence. Credential/config resets, bulk `removeExtensionConnections`, and subject changes ROTATE or delete a UNIQUE OPAQUE generation TOKEN (a fresh Symbol at every probe reservation/reset/detach; Symbol identity means a missing/deleted token can never compare equal to a detached old probe's token, even across same-id reinstall). A stale in-flight result settles only for its original caller and never repopulates the cache or overwrites connectionHealth — even when the new probe completes FIRST and the old one settles LAST (reverse settlement), and even when the effective connector subject changed mid-flight (the old subject probe is detached before the new subject probe starts). SETTLED CACHE AND IN-FLIGHT EVIDENCE FORM ONE GENERATION CONTRACT: every cache entry stores the token it was captured under and is reusable ONLY when that token is exactly the current token (plus subject/TTL match); reserving ANY genuinely new probe (force, expired/missing cache, changed subject) deletes the prior settled cache and rotates the token BEFORE network work starts; and for the same current subject/token the CURRENT in-flight probe is checked and joined BEFORE any settled entry is served, so a non-force caller arriving during a forced refresh joins the refresh and can never bypass it with older settled evidence (force still bypasses settled cache and joins an already-current same-subject in-flight probe). Live health is always recorded by the current-token probe (an explicitly null checkedAt is preserved for invalid clocks; only caching is skipped then). Cache hits and joins return the TRUE network probe `checkedAt` — cache access never refreshes evidence time. A failed real business request (network/timeout, 401, 403, other non-2xx, oversized, invalid JSON) detaches prior connector-test evidence before recording the actionable health result, so the next action must obtain fresh safe-test evidence (a failing fresh test sends zero business requests). `warmRemoteLifecycle({ concurrency })` probes enabled extensions/connections in the background with a FROZEN max concurrency of 4 for every caller input (99/Infinity/invalid clamp to 4; 0/negative degrade to 1; zero-job runs settle immediately), catches per-extension failures, and never blocks server startup; a safe enumeration seam (`manager.getEnabledRemoteExtensionIds` wired as `listEnabledRemoteExtensions`) covers enabled manager-owned Remote extension ids EVEN when their executable root is excluded by a persisted required-update block, so a superseded block can clear and the root can return. `getWorkbenchCatalog` includes a safe extension-level lifecycle summary produced by a strict ALLOWLIST normalizer (only the documented status/health enum strings, a valid timestamp string or null, stable safe codes, and a boolean consent flag survive; every object/array/unknown-shaped value is dropped, so an injected callback can never relay arbitrary nested data, hashes, keys, paths, or secrets): required/trust_invalid extensions are visibly blocked, unreachable is a warning that keeps read-only capability. Action responses are classified by HTTP status BEFORE any body parsing (non-JSON 401→`connector_unauthorized`/unauthorized, non-JSON 403→`connector_forbidden`/forbidden); every other post-request failure — oversized body or invalid JSON on a 2xx included — sets health to unreachable with a stable code, so the preflight probe's reachable evidence is never left standing after a real action request failed.

## Security invariants

- Manifest entries must stay inside the installed extension directory.
- Connectors are fixed HTTP(S) base URLs without embedded credentials.
- Connector origins must be explicitly declared in `permissions.network`.
- Actions use fixed connector-relative paths and declared methods.
- Action IDs, connectors, permissions, tool/surface relationships, and installed Artifact action subsets are checked server-side.
- `ask` actions return `confirmation_required` before any upstream request.
- `api-key` and `issued-key` credentials are stored server-side with owner-only file permissions and are injected only on the final Gateway request. Legacy `env-bearer` values remain server environment-only.
- Credential placement is Header-only; unsafe and host-reserved headers are rejected. Provisioning requires HTTPS except loopback development and an explicitly allowed Origin.
- Connection APIs return credential metadata plus ephemeral `unknown/reachable/unreachable/unauthorized/forbidden` health evidence and its last-check timestamp. `configured` never means `reachable`; health resets after credential replacement or process restart and is never an authorization source. Access Keys, setup codes, provisioning URLs, and raw credential responses never enter registry/view responses or Agent output.
- Third-party APIs own Key scopes, revocation, RBAC/ABAC, and final business authorization. Gateway maps `401`/`403` without inventing a second business permission system.
- Upstream requests have a timeout and bounded JSON response size.
- Every managed extension root is rechecked against the signed OCIX file-hash index before it is exposed to the runtime. A missing or mismatched integrity record quarantines both Host surfaces and managed Agent Tool/Skill files while keeping the installation visible for reinstall or recoverable uninstall; an edited Native bundle, Declarative definition, HTML Artifact, or manifest is never loaded.
- `ask` actions use a short-lived, one-time confirmation challenge bound to the extension, surface, originating Tool, instance, action, and exact input. A client-side `confirmed: true` flag is not an authorization signal and is ignored.
- Native assets are served only from the exact verified source per delivery mode: Local and Hosted from installed/materialized files (never arbitrary internet URLs), Remote from the exact signed lazy resource resolved through the manager-owned resolver (never arbitrary URLs).
- New `.ocix` and marketplace catalogs carry their Ed25519 public key inside the signed document. Inspection proves signature self-consistency and returns only identity, fingerprint, permissions, and Agent Runtime inventory; first trust still requires an explicit fingerprint confirmation.
- Packaged Agent Tools and Skills are validated before installation. Tool names match their file names, use one default export, cannot replace reserved built-ins, and Skill frontmatter must match its directory.
- For local managed OpenCode, enabled OCIX Tools are copied as OpenChamber-owned global Tools in `~/.config/opencode/tools`; Skills are copied to `~/.config/opencode/skills`. Persisted owner/version/hash metadata drives enable, disable, update, rollback, and uninstall.
- Reconciliation never overwrites unmanaged or externally modified global files. Global file changes and manager-state writes roll back together on failure. A bounded allowlist of exact hashes for previously shipped OpenChamber built-ins supports one-time ownership migration and upgrade; a file with any other hash remains user-owned and produces a conflict.
- Every OpenChamber-owned Tool/Skill write has a publisher/extension-namespaced ownership record under `<resolved-opencode-config>/openchamber`. Install records contain owner and install-time hash; update/uninstall changes only matching files. A user-modified global file is preserved and reported as a conflict.
- Hosted OCIX accepts only HTTPS manifest/resource URLs (loopback HTTP is development-only); redirects are followed manually with a small bound and every next hop is validated against the ORIGINAL origin plus the HTTPS/loopback-http/no-credentials policy BEFORE contact (cross-origin, scheme change, credential-bearing, missing/invalid Location, or redirect-limit overflow fail closed without ever contacting a forbidden target; an unexpected cross-origin `response.url` is rejected defensively). It verifies publisher signature, every resource SHA256, and actual HTTP `Content-Type` against the signed `mimeType`, validates minimum runtime, reads bodies with a streaming-bounded reader that cancels on overflow, and materializes only normalized OCIX surfaces. A failed fetch, signature, hash, MIME, or compatibility check may keep only a last-good version whose local cache still passes a fresh exact-file integrity scan.
- Remote inspect performs no trust, install, secret, or resource write and never fetches `resources[]`. Remote connect refetches and reverifies the signed manifest (TOCTOU safe), requires the exact locally derived publisher fingerprint plus manifest hash, rejects connecting an already installed extension, then persists trust and the Remote shell before handing the access key to the existing `runtime.configureRemoteConnection`; the route validates the key with the shared opaque `validateRemoteAccessKey` (non-empty, length-bounded, no unsafe C0/DEL control characters) synchronously BEFORE `manager.connectRemote` — before any trust, staging, Manager state, Agent Runtime, or Secret Store write — and preserves the exact string byte-for-byte (leading/trailing spaces are valid credential material and are never trimmed); `setRemoteCredential` uses the same validator so route and store cannot drift, and `trustAdded`/`installationId` rollback bookkeeping never appears in the public response — `connectRemote` returns ONLY the public extension/connector fields plus a NON-ENUMERABLE opaque manager-owned capability bound to that exact installation (configure/remove/rollback OPERATIONS, never raw ids), which the route uses exclusively; the credential runtime is bound ONCE at connect creation (a private internal argument), the capability accepts NO caller-supplied runtime/store/manager and exposes only `configureCredential(accessKey)`, `removeCredential()`, `rollback()`, direct connects without a bound runtime still roll back while configure/remove fail with a controlled non-sensitive error, `rollbackRemoteConnect` is manager-private, and the capability's rollback still refuses stale installations and the runtime credential store still binds the installation, so it cannot be forged or reused against another installation. Every connect generates one cryptographically random `installationId` that binds the shell metadata, the credential record, and the failure-atomic rollback. Credential storage uses an installation-bound store setter (refuses to overwrite a different installation's record with `remote_installation_conflict`) and a conditional remover (deletes only the exact installation's record; a stale cleanup returns a non-sensitive mismatch indicator), exposed through `runtime.configureRemoteConnection`/`runtime.removeRemoteConnection`; the generic PUT/DELETE connection APIs keep using the generic store methods, and both generic and Remote credential deletion work without the extension shell (orphan cleanup) — only configuring requires a valid installed connector. If credential storage/configuration fails, the route runs `connected.capability.removeCredential()` then `connected.capability.rollback()` — the manager-private capability closure applies the captured `installationId`/`trustAdded`; the route never calls `manager.rollbackRemoteConnect` and never receives or passes an installation id. The private rollback refuses ALL mutation when the current active Remote metadata belongs to a different installation (`remote_rollback_installation_changed`, 409) and removes the publisher trust key only when this operation added it and no remaining installed version still references that publisher id/keyId; the original error is preserved with sanitized recovery details. Access keys and installation ids never appear in API responses, PUBLIC manager snapshots, trust JSON, logs, or the review UI. Storage boundary: access keys live ONLY in the private Secret Store (never in manager installations metadata), while installation ids live only in private durable Manager and Secret Store records because they bind shell/credential/rollback ownership.
- Before ANY trust, shell, Manager state, Agent Runtime, or Secret Store write, both `inspectRemote` and `connectRemote` run one shared write-free preflight on the signed manifest's extension document: (a) the SAME single-sourced runtime metadata normalization used at load time (`normalizeExtensionManifest`) — connectors (auth type/placement/baseUrl vs `extension.permissions.network`), actions and connector references, views/artifacts/dashboard/routing, Native `trust.mode`, duplicate identities; (b) every shell-consumed resource reference (declarative/native/HTML entry and icon) must be a safe declared `resources[]` path using the Hosted OCIX kernel path rules (`safeRelativePath`) plus the runtime entry-extension rules — traversal such as `../../escape.txt` and missing/ambiguous references are rejected; and (c) the exact hosted Agent Runtime surface-tool binding constraints shared with materialization (`hostedSurfaceBindings`: tool pattern, reserved OpenCode built-ins, duplicate/cross-surface conflicts). All three layers reuse the pure helpers that later materialization uses, so the rules cannot drift. A signed-but-runtime-invalid manifest rejects with the stable runtime/kernel code (e.g. `network_not_allowed`, `invalid_manifest`, `invalid_hosted_resource`, `invalid_entry`, `invalid_hosted_agent_tool`) and leaves no trust, state, shell, Agent Runtime, or credential writes behind; the selected connector is cross-checked against the normalized metadata to keep the exact-one-`api-key` policy single-sourced. Credential/secret mutations that span the Manager, Secret Store, and Workbench are serialized by a mutation coordinator scoped PER MANAGER INSTANCE (WeakMap-keyed): two route registrations sharing the same manager serialize, unrelated manager/runtime/data-directory instances never block one another, and failures never poison later operations; read-only routes are uncoordinated, and installation-identity matching remains defense in depth for direct/internal callers. Extension uninstall runs ALL fallible external cleanup (credentials, Workbench tiles) FIRST while the shell still exists and calls `manager.uninstall` only after cleanup succeeds — a cleanup failure leaves the extension installed (any remaining secret still has an owner) and the response never claims extension removal.
- A Remote shell is re-verified on enable, initialization, runtime exposure, and Agent Runtime reconciliation against the CURRENT trusted publisher key: the trust-record public key is normalized and re-fingerprinted locally, and the reverified embedded publisher id, keyId, normalized public key, and fingerprint must exactly match both the persisted metadata and the accepted manifest keyId; any mismatch fails closed (`publisher_untrusted` or `remote_shell_integrity_failed`) and quarantines the shell. A manifest whose embedded publisher key differs from the current trust record is never accepted on the strength of its own self-consistent signature.
- Remote lazy signed resource loading (Phase R2): resolution follows a TWO-PHASE queue contract. The SHORT phase A (inside the manager-scoped mutation queue) runs the central classifier, validates the exact relative path, finds the exact currently reverified signed resource, checks the approved origin, and captures an IMMUTABLE plan (extensionId, an allowlisted deep SCALAR snapshot of the authority fields the classifier actually consumes — directory, extensionHash, signedManifestHash, provenance.generation, never the caller-owned reference — exact resource tuple path/url/mimeType/sha256, accepted manifestHash, origin; nested provenance, authority snapshot, resource tuple, and plan are all frozen). The NETWORK/CACHE phase B then awaits the manager-owned in-memory TTL cache's verified fetch OUTSIDE the mutation queue — no global queue is held during network I/O, so one slow/broken Remote cannot block unrelated extensions or lifecycle mutations (entity isolation), and uninstall/failed-connect rollback proceed while a Remote fetch is paused. A SHORT phase C re-enters the queue BEFORE returning bytes: it re-runs the SAME central classification against the IMMUTABLE captured authority snapshot from phase A (never the caller-owned authority reference) and fails closed with a stable sanitized code if the extension was removed, disabled, reconnected with a different accepted manifest, replaced by another delivery, or its exact resource tuple/origin changed — a stale in-flight resolve NEVER serves bytes after uninstall/rollback/reconnect/disable (the cache's per-extension clear epoch stops the old in-flight fetch from repopulating after clear, and phase C never clears a replacement installation's cache on postflight denial). Ordinary/current Local null and authorized current Hosted verified reads retain their short queued behavior and are not weakened. The manager resolver is AUTHORITATIVE and is consulted for EVERY runtime entry read (extensionId + exact manifest entry) BEFORE any disk read, bound to a captured AUTHORITY context: at the moment the runtime reads and parses openchamber.extension.json it records (in an internal WeakMap, never exposed in registry/views/API responses) the resolved extension root, the TRUE canonical SHA-256 of the captured parsed pre-normalization document (stable key-sorted canonicalStringify JSON, so key order and whitespace cannot change it), and the SHA-256 of the sibling signed Hosted manifest (captured through ONE bounded no-follow open handle — O_NOFOLLOW|O_NONBLOCK where supported, open-handle stat requiring a regular non-empty file within the single-source 2 MiB Hosted manifest transport bound shared with the manifest fetch BEFORE any allocation/read, fixed-buffer read of at most that verified size through the same handle, close in finally; a symlinked/non-regular/oversized/shrunk/grown sibling fails closed with no hash — so a valid signed manifest in (512 KiB, 2 MiB] still captures its hash; the extension manifest itself stays at 512 KiB). The manager requires that context and binds every resolution to it: a captured root OUTSIDE the managed versions directory is a configured/built-in Local root (null disk fallback allowed); a missing extension with a captured MANAGED root fails closed (`remote_shell_missing`) so a stale/recreated managed path can never serve bytes; manager roots are issued to the runtime as STRUCTURED descriptors carrying an opaque lifecycle GENERATION — a private persisted `generationId` set at every install/connect (sanitized from all public output), created ONLY by current install/connect — `initialize` never synthesizes or migrates it for any pre-existing record (parent AGENTS.md: no compatibility layers/fallbacks/migrations) — captured with the exact manifest authority. ONE central manager classifier (shared by the `authorizeExtensionAuthority` callback and `resolveExtensionResource`, both inside the mutation queue) decides every manifest: the runtime awaits authorization for EVERY discovered manifest AFTER capturing the authority and BEFORE exposing it to any metadata/operation consumer (list, Workbench catalog, routing capabilities, connections, view/artifact/connector lookup, configure/provision/test, invokeAction), so a configured root can never resurrect a disabled or integrity-quarantined manager extension id and an extension record is therefore matched by manager-issued provenance + current generation, never by extension id alone. Public runtime load errors are SANITIZED: registry/Workbench/connection responses carry only a stable allow-shaped code (the controlled error.code when safe, otherwise `extension_load_failed`) plus a fixed non-sensitive message and an optional safe extension id — never manifest paths, directories, raw filesystem error text, data/versions/configured roots, or secret/internal authority material, which stay in server-internal logger calls. A configured/built-in ordinary root colliding with a record's id (no provenance) fails closed, as does a missing record with a captured manager-issued root (`remote_shell_missing`, even for a stale Hosted cache root outside versionsDirectory). A NO-RECORD, NO-PROVENANCE authority whose directory resolves to the managed versions tree itself or anywhere below it is ALSO rejected with `remote_shell_missing` (component-correct containment via the injected `pathImpl`: only an exact parent `..` or `../` counts as outside, so a legitimate descendant whose first component merely starts with two dots, e.g. `..managed`, is still inside), so a plain configured root pointed at a recreated managed path after uninstall can never be authorized or null disk-fallback; the classifier additionally compares canonical realpaths when the versions tree exists, so an outside LEXICAL configured root that is a symlink/alias into the managed tree is rejected too (an authority root that cannot be canonicalized because it vanished/changed fails closed; a missing versions tree skips only the canonical-base comparison); only a no-record, no-provenance root OUTSIDE the managed versions tree is ordinary. Null fallback is ONLY for ordinary configured/built-in roots with no record and for an authorized current Local install (enabled, exact active managed directory, current Local generation, reverified signed installed-file integrity). Hosted and Remote manager-owned bytes are NEVER null-fallback: an authorized current Hosted install (enabled, EXACT verified last-good Hosted cache root, current Hosted generation that includes the last-good manifest hash — a Hosted refresh/update changes the generation and invalidates stale roots, and the captured canonical extension-hash and sibling signed-manifest hash must match the current reverified signed Hosted document) is read INSIDE the same mutation-queue operation that authorized it — the exact cached file is opened no-follow/nonblocking where supported, fstat-verified as a regular non-empty file within an explicit 8 MiB manager bound, read with a bounded loop from that same handle, and hashed against the current signed/integrity file map before being returned (arbitrary/undeclared paths fail closed; the runtime never reads Hosted by unlocked pathname); a Remote resolution returns verified bytes through the manager-owned cache. A stale inactive version root, a generation mismatch (uninstall/reinstall, same-version cross-delivery path reuse after Remote->Local, Hosted update), an unknown/corrupt delivery value, or a disabled extension all fail closed (`remote_shell_integrity_failed` / `remote_shell_disabled`); a current Remote resolution additionally requires the captured root to be the exact active managed directory UNCONDITIONALLY (an outside-managed capture is always stale/forged, even with valid hashes), plus the accepted signed-manifest and canonical extension hashes, and the lifecycle generation is the private persisted `generationId` with NO `installationId` compatibility fallback (a record without it fails closed / issues no root until it is reinstalled/reconnected; `installationId` keeps its separate credential/rollback ownership role); for the current Remote the captured root must be the EXACT active managed version directory, the captured signed-manifest hash must equal the accepted manifest hash (the accepted hash is the generation binding — a reconnect with an identical signed manifest yields identical metadata/resources, a different one is rejected), and after the current-key/shell re-verification the captured extension-document hash must equal the same canonicalStringify digest of the reverified signed manifest's extension document; then the EXACT declared `resources[]` path is looked up (unknown/unsafe paths fail closed), the final/request origin must be in the granted `resourceOrigins`, and the fetch enforces the same HTTPS/schema rules from the verified manifest (the initial resource URL is normalized with the same HTTPS/loopback-http/no-credentials policy BEFORE the first request), normalized Content-Type against the signed `mimeType`, the per-resource size cap, and the exact signed sha256 — a failed fetch/MIME/hash/origin/size validation exposes no bytes and creates no usable cache entry, and the Remote Access Key never enters resource request headers/body/URL, cache data, responses, logs, or errors. Resolver bytes win even over a disk-present file (an inserted file/symlink can never serve unverified bytes); a resolver failure is a stable sanitized error and NEVER falls back to disk; a KNOWN disabled Remote extension fails closed with a stable sanitized error (`remote_shell_disabled`) instead of returning null; only a null result for ordinary configured/built-in roots with no record and for authorized current Local installs — as determined by the manager — uses the exact disk path without any remote fetch/cache. A missing extension is NEVER allowed a disk fallback when its captured root is under the managed versions directory: it fails closed with `remote_shell_missing` even if the path was recreated after lifecycle removal. Both the Hosted manifest transport (used by Remote inspect/connect) and resource loads follow redirects with a small bounded manual loop: every next hop is resolved against the ORIGINAL requested origin and re-validated with the HTTPS/loopback-http/no-credentials URL policy BEFORE it is contacted, redirect bodies are awaited-cancelled, and cross-origin, scheme change, credential-bearing, missing/invalid Location, or redirect-limit overflow fail closed without ever contacting a forbidden target (an unexpected cross-origin `response.url` is rejected defensively). Response bodies are read with a streaming-bounded reader that accumulates only up to the size limit, cancels immediately on overflow (an unbounded chunked body is never fully consumed), always releases the reader lock (including after cancel-on-overflow), keeps the declared Content-Length early rejection, and every OTHER pre-consumption rejection (invalid/cross-origin response.url, redirect-limit, missing/invalid Location, non-OK status, missing/MIME-mismatch Content-Type, declared-length oversize) best-effort cancels the response body so hostile streams are never retained across retries. Verified bytes are cached in a MANAGER-OWNED, PROCESS-LIFETIME IN-MEMORY TTL cache keyed by extensionId + exact resource path + signed resource digest + accepted manifest hash (intentionally NON-DURABLE: a process restart drops all entries, which is safe early invalidation). The store holds DEFENSIVE COPIES of the verified bytes plus exact metadata, cachedAt, expiresAt and size; the stored Buffer is never exposed and every caller receives a copy, so mutation cannot corrupt the store or another caller. cachedAt is taken AFTER the verified network fetch completes (never before), expiresAt = cachedAt + ttlMs is stored explicitly, and clock validity is enforced by ONE helper accepting only a non-negative safe integer whose sum with ttlMs is ALSO a safe integer — BOTH the pre-fetch now and the post-fetch fetchedAt are checked before serving/fetching/inserting, so NaN/Infinity, fractional, negative, and overflow-near-MAX_SAFE_INTEGER clock results are rejected outright (nothing is served, fetched, or cached under them) and an entry is never inserted with an immediately invalid expiresAt. A hit is valid only when 0 <= now - cachedAt <= ttlMs (30 minutes, INCLUSIVE upper bound: a hit remains valid at now === expiresAt and expires only at expiresAt + 1; any negative age, i.e. future-dated, is invalid) AND the stored bytes re-hash to the signed sha256 on EVERY hit; an expired, future-dated, malformed, size-inconsistent, metadata-mismatched, or tampered entry is deleted ONLY for that key and never served, and an offline refetch then fails hard and sanitized (never stale bytes). FIXED GLOBAL PRODUCTION LIMITS (injectable in tests): at most 512 entries and at most 64 MiB of raw verified bytes, enforced atomically before insertion with TRUE oldest-first eviction (entries sorted by cachedAt, not Map insertion order); a same-key replacement is excluded from the capacity calculation before the bounds are checked, and a single entry larger than the global byte limit fails closed; there is NO filesystem scan, scan-node constant, or path budget. ACCOUNTING IS CORRUPTION-PROOF: there is no mutable incremental byte counter — before every insertion the store is sanitized/recomputed (per-key schema/identity/Buffer/safe-integer-size-exactly-equal-to-bytes-length/finite-clock validation; malformed, expired, and future-dated entries are deleted per key WITHOUT throwing, and bytes are summed from SURVIVING buffers only), so an injected or mutated entry (missing/non-numeric/changed size, non-Buffer, wrong schema, bad clock) can never produce NaN or an undercount, and a malformed unrelated entry neither blocks nor influences accounting or eviction. PER-ENTITY ISOLATION: validation/removal of a malformed or expired entry never throws in a way that blocks an unrelated extension, and one extension's fetch/cache failure never poisons other keys. SAME-KEY COALESCING: concurrent resolves for the same key share one verified fetch; the shared in-flight promise resolves to the INTERNAL verified buffer and EVERY caller copies it, so coalesced callers each receive their OWN Buffer (mutating one cannot alter the other or the cached entry); the in-flight entry is cleared in finally and a failed fetch never caches bytes or poisons retries, while different keys/extensions stay independent. CLEAR VS IN-FLIGHT: uninstall and failed-connect rollback call clearExtension, which increments a per-extension invalidation epoch and removes that extension's stored entries WITHOUT ever throwing on malformed entries (only well-formed records owned by the extension are removed via an isRecord gate; null/undefined/primitive/identity-less malformed entries are skipped and left for the next recompute sanitize — semantic cleanup, no filesystem removal can fail) before the durable state removal; a resolve captures its epoch, so a resolve AFTER clear does not join a pre-clear in-flight promise, an in-flight fetch inserts only when its epoch is unchanged (an already-started caller may still settle with its verified bytes but never repopulates the cache after clear), and an old promise's finally never deletes a newer in-flight record.
- Hosted cache integrity covers the original signed Hosted manifest, the generated runtime manifest, every signed remote resource, and every deterministic Agent Tool shim. Before enable, process initialization, runtime exposure, or Agent Runtime reconciliation, OpenChamber re-verifies the cached manifest with the currently trusted publisher key, rebuilds the expected integrity index from that signed document, and then hashes the exact local file set. A missing/untrusted signature, edited integrity record, symlink, extra file, missing file, or hash mismatch fails closed.
- Hosted permission, origin, action, credential-scope, or Native-code expansion creates a pending update and requires a new explicit confirmation. Native surfaces also require `trust.mode = "native-code"`. Permission-equivalent updates may advance automatically after TTL refresh.
- Hosted pages cannot call arbitrary network APIs. Resource loading is owned by the Hosted loader; business calls use a generated lightweight global Tool shim and the existing Business Gateway. Connector credentials remain server-side and the third-party server remains responsible for key RBAC/ABAC and revocation.
- Optional `agentRouting`, `views[].routing`, and `artifacts[].routing` metadata is validated at package and runtime load. Identifiers, counts, priority, operation, data-authority enums, and multi-surface declarations are bounded.
- The capability route exposes only extension/tool/intent/operation/data-authority IDs plus coarse connection state. It excludes examples, display names, Connector origins, credential identifiers, Keys, Tokens, and business response data.
- The fixed routing prompt prioritizes matching business Tools over generic generated UI, caps output at 12,000 characters, and tells external runtimes to call only Tools actually present in their current Tool set.
- Artifact envelopes use an independent exact schema and are revalidated on both client and server. The envelope is capped at 256 KiB, HTML at 192 KiB, markup at 4,000 elements, and display height at 120-900 px.
- `artifact-store.js` stores content-addressed documents under the OpenChamber data directory with owner-only permissions and atomic directory replacement. The hash covers executable content, so title or display metadata cannot create duplicate documents.
- `workbench-store.js` stores Generated Interactive UI, Generated HTML Artifact, and pinned MCP App envelopes as immutable, content-addressed snapshot records under the Workbench data root. A read recomputes the digest and rejects a malformed, missing, oversized, or content/reference-mismatched record; the mutable Board stores only the current snapshot reference.
- Replacing a generated Tile snapshot is a compare-and-swap operation. The caller supplies the active Board `expectedRevision`; the Store runs under the project write lock, rechecks Tile ownership and form, writes the complete immutable snapshot first, and only then increments the Board revision and atomically publishes the new reference. A stale revision or failed snapshot write leaves the previous Board pointer authoritative.
- A pinned MCP App snapshot cannot change its AppBridge authority while updating result/model context. `server`, `resourceUri`, and `toolKey` must exactly match the previously persisted snapshot or replacement fails with `workbench_snapshot_binding_mismatch`. Installed Tiles cannot use this generated-snapshot replacement route.
- History replay calls `materialize` again. Cache deletion is safe because the Tool result remains the source of truth and deterministically recreates the same Artifact ID.
- Cached metadata and document bytes are compared with the document deterministically derived from the authoritative Envelope. Missing or mismatched entries are atomically rebuilt instead of being trusted by ID alone.
- Static documents reject non-fragment `href`/`xlink:href` targets at materialization. Relative subresources that remain useful in authored markup are still blocked by document CSP; the Chromium verifier asserts that no request reaches the loopback target.
- Static scanning rejects frames, objects, embeds, forms, base/link/meta refresh, remote resources, scripts in static mode, and network/eval/worker/WebAssembly/service-worker primitives in interactive mode. Browser enforcement remains authoritative.
- Static document CSP uses `default-src 'none'`, inline style, data/blob images, and no script. Scripts mode is served through a trusted Broker whose response may frame only a `data:` child and whose nested Artifact document injects its own `frame-src 'none'` CSP. Neither layer enables `unsafe-eval`, network, workers, forms, plugins, or external frames.
- CSP/sandbox declarations alone are not proof that a scripted Artifact emits no requests. Scripts therefore run in an opaque `data:` child behind the Broker, which relays only strict Bridge envelopes and removes the child after a navigation. The Chromium attack matrix observes form, frame, download, self-navigation, meta-refresh and API attacks while asserting zero actual target requests. Managed Desktop additionally hosts the Broker in a unique-partition `WebContentsView` with no main-world Electron API and main-process lease, concurrency, CPU and memory gates; Stop destroys the renderer. Browser process placement is still not independently controllable on ordinary Web, so Web Scripts remain experimental and default-off.
- Generated interactive documents receive a deterministic Bridge bootstrap. It applies allowlisted `--ocix-*` tokens and emits ready/resize/error/heartbeat messages; it does not expose Gateway, Tool, filesystem, storage, cookie, or credential APIs.
- Signed installed HTML documents receive a distinct Business Bridge. `query/execute` emit bounded `artifact.businessRequest` messages; the Host derives extension/Artifact identity, enforces the Artifact's declared action subset and existing confirmation policy, injects credentials server-side, and returns only data or sanitized errors. Raw Connector URLs, Keys, Tools, MCP, storage, and direct network remain unavailable.
- Artifact document responses are private/no-store, nosniff, no-referrer, and permission-restricted. `frame-ancestors` allows the same HTTP OpenChamber origin and the exact packaged Desktop origin `openchamber-ui://app`; no other web or custom-protocol parent is allowed.

Production package signatures, persistent install records, publisher confirmation, lifecycle management, signed static marketplace catalogs, OCIX Connector Authentication v1, first-party Hosted OCIX thin-package delivery, Phase R1 Remote connect (signed-manifest URL + access key, embedded publisher verification, discovery-only shell, server-side secret handoff with failure rollback), Phase R2 Remote lazy signed resource loading (re-verified exact `resources[]` lookup with granted-origin/redirect/MIME/size/SHA enforcement, short verified TTL cache, mutation-queue serialization, and lifecycle clearing), and Phase R3 Remote health + signed-manifest updates (bounded/coalesced probes, automatic metadata-only apply for permission-equivalent/reduced updates, re-consent for expansion/native/key rotation, required-update blocking, actionable business-gateway failures, startup/surface/Workbench/manual-test triggers, safe diagnostics, and Extension Manager/Workbench UI) are implemented. A signing key proves origin-key possession and integrity, not code safety, real-world publisher identity, or business API access. Public hosted Marketplace operations, signing-key revocation/transparency, malware review, and remote OpenCode installation remain separate work.

## Developer tooling

Create and validate a repository-compatible mixed Interactive UI + HTML Artifact starter from the repository root:

```bash
node scripts/interactive-ui-extension.mjs create /absolute/new/path --id com.acme.operations --name "Acme Operations" --tool-prefix operations
node scripts/interactive-ui-extension.mjs validate /absolute/new/path
```

Create and validate a manifest-only Hosted OCIX thin package:

```bash
node scripts/interactive-ui-extension.mjs create /absolute/new/hosted-path \
  --delivery hosted \
  --id com.acme.hosted \
  --name "Acme Hosted" \
  --manifest-url https://apps.example.com/manifest.json \
  --initial-permissions /absolute/hosted-permissions.json
node scripts/interactive-ui-extension.mjs validate /absolute/new/hosted-path
```

The same `pack` and `verify` commands handle Local and Hosted delivery. Hosted source validation and packaging reject every file other than `openchamber.extension.json`.

Validation reuses this runtime for discovery, manifest normalization, entry containment, descriptor/bundle/HTML hardening checks, then adds static Declarative primitive/binding/action checks. It substitutes non-secret placeholder values for referenced environment variables, never calls upstream business APIs, and never executes Native code.

The starter manifest includes namespaced `agentRouting` metadata and per-surface routing for Declarative, Trusted Native, and HTML Artifact examples. Developer examples are retained for test corpora and review but are deliberately excluded from the Agent system context to prevent free-text prompt injection.
